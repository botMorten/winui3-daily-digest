## Community experience

- **Reactor’s early feedback: less binding plumbing, but where’s the visual workflow?** — Microsoft blog comments, October 21–22. Luca Spolidoro likes fewer files and avoiding bindings but says he would miss a designer; Ed Kolis welcomes compile-time checking while asking about a preview pane; Alex Stefano Falcon Flores is interested in mixing Reactor with XAML and asks about hot reload. ## News/releases

- **Microsoft.UI.Reactor gets a full C#-first WinUI walkthrough** — #ifdef Windows, October 21, 15:00 PDT. Reactor describes UI in C#, reconciles changes onto native WinUI controls, and supports coexistence with XAML in the same visual tree. The article demonstrates a .NET 10 file-based app through WinAppCLI and discusses analyzers, layout and control wrapping. Practical takeaway: an incremental experiment for teams comfortable with MVU, not a reason to rewrite a working MVVM application. Microsoft explicitly offers no support policy or API guarantees. This is a new article about an existing experiment; its illustrated preview.16 package was released September 22, not yesterday. [Announcement](<https://devblogs.microsoft.com/ifdef-windows/microsoft-ui-reactor-a-c-first-way-to-build-winui-apps/>).

## microsoft-ui-xaml — past 24 hours

**Exact window:** October 21, 2026, 08:30 PDT → October 22, 2026, 08:30 PDT. Issues and enabled GitHub Discussions inspected directly, including older threads’ fresh comments/replies.

- **Community designer VSIX announced just before cutoff** — Discussion [#12369](<https://github.com/microsoft/microsoft-ui-xaml/discussions/12369>), October 22, 08:27 PDT; also posted on the longstanding designer issue. 0x5bfa says the extension integrates with Visual Studio’s designer host; VS2022 support remains work in progress. Its repository specifies C# only, no x86, no `Window` preview, and Windows App SDK 2.5.1 required. Potentially useful for eligible projects, but the author’s speculation about Microsoft’s internal designer plans is not confirmation. [Project and limitations](<https://github.com/0x5bfa/WinUIDesigner>).

- **NavigationView clipping moves from proposed fixes to merged code** — older issues [#9034](<https://github.com/microsoft/microsoft-ui-xaml/issues/9034>) / [#5854](<https://github.com/microsoft/microsoft-ui-xaml/issues/5854>) and [#9789](<https://github.com/microsoft/microsoft-ui-xaml/issues/9789>). On October 22 UTC, PR12321 merged a first-render hamburger/pane-toggle sizing fix; PR12316 merged a `LeftMinimal` header-padding fix when both navigation buttons are hidden. This materially advances previously reported work. No released-package availability was established.

- **Embedded XAML resource lifetime fix merged** — issue [#11058](<https://github.com/microsoft/microsoft-ui-xaml/issues/11058>), originally April 9. PR12128 merged October 22 UTC and the issue closed: the change retains ownership of resource memory instead of freeing embedded XAML bytes before consumption. Relevant to affected resource-loading failures; again, source integration—not proof an installed SDK contains the fix.

- **Chart feedback becomes a concrete Fluent-style issue** — new issue [#12362](<https://github.com/microsoft/microsoft-ui-xaml/issues/12362>), October 21, plus fresh replies on Discussion [#12343](<https://github.com/microsoft/microsoft-ui-xaml/discussions/12343>). The reporter requests changes to fonts, legends, grid lines, gradients and tooltips; a Microsoft participant acknowledges it without committing a fix or release decision. Discussion replies point to the existing API specification and debate customization. A participant attributes self-contained deployment restrictions to resource loading, but explicitly makes no GA promise: do not treat shared deployment as fixed.

- **Misleading navigation exception gets a detailed reproduction** — issue [#5075](<https://github.com/microsoft/microsoft-ui-xaml/issues/5075#issuecomment-6321612523>), originally May 2021; new October 21 comment. dotMorten posts Copilot-assisted diagnostic results reporting `Frame.Navigate(UserControl)` produces `NullReferenceException`/`E_POINTER` before `NavigationFailed`. The practical correction is to navigate to a `Page`, or host the control in `ContentControl` when page navigation is unnecessary. A clearer framework diagnostic is proposed, not implemented or maintainer-confirmed here.
