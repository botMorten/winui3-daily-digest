## Community experience

- **AppInstance startup can hang after process-ID reuse.** WindowsAppSDK issue, filed October 13: <https://github.com/microsoft/WindowsAppSDK/issues/6860>. A reporter diagnosed Snipping Tool on an Insider build using runtime 2.5.1, supplying wait chains, debugger stacks and a reproduction sequence in which an unrelated process inherits a stale PID. Their source analysis points to unbalanced mutex ownership in `GetInstances()`/`FindOrRegisterForKey()`; terminating all affected app processes restored operation on their machine. This is relevant to WinUI apps using SDK single-instancing, not merely a shell anecdote. Root cause and proposed bounded-wait/liveness changes remain reporter claims, with no maintainer-confirmed or shipped fix verified.

- **Generated TabView apps break into the debugger on restore.** WindowsAppSDK issue, filed October 13: <https://github.com/microsoft/WindowsAppSDK/issues/6862>. The reporter’s corrected tests reproduced a first-chance `ArgumentException` in `winui-tabview` on all three minimize/restore cycles: a temporarily negative `TitleBar.RightInset` reaches `MinWidth`. **Correction:** `reactor-tabview` did not reproduce it because it reads the inset only at startup: <https://github.com/microsoft/WindowsAppSDK/issues/6862#issuecomment-6152612901>. An open fix PR clamps with `Math.Max(0, RightInset)`; its author reports five clean post-change restore cycles, but it is **unmerged**, not a released template fix: <https://github.com/microsoft/WindowsAppSDK/pull/6863>. The app reportedly continues without a debugger, making this particularly confusing during F5 development.

- **A target-framework suffix, not .NET 10 itself, blocked this build.** WindowsAppSDK issue filed October 13, with new diagnostic follow-up October 14: <https://github.com/microsoft/WindowsAppSDK/issues/6859#issuecomment-6162361225>. The developer reports successful tests with .NET 8, 9 and 10, but failures for tested Windows target versions ending in `.1`; `10.0.26100.0` worked where `10.0.26100.1` did not. They now have the project building and describe the property-editing experience as fragile. Practical lesson: compare the exact TFM against documented supported values and let restore finish; this is one developer’s tested resolution, not evidence that .NET 10 is generally broken.

## microsoft-ui-xaml — past 24 hours

**Exact window:** October 13, 08:30 → October 14, 08:30 PDT. Older threads below have verified new activity inside this window.

- **Bound `x:Load` in ControlTemplates gets a merged compiler fix.** Issue #7086, originally May 11, 2022: <https://github.com/microsoft/microsoft-ui-xaml/issues/7086>. On October 13, the issue closed as PR #12239 merged, separating the template binding root from the visual/name-lookup root to repair generated C# and C++/WinRT references: <https://github.com/microsoft/microsoft-ui-xaml/pull/12239>. Deferring the template’s visual root remains unsupported. This is a **merged source fix**, not verified package shipment; don’t assume an installed SDK already contains it.

- **TableView’s missing multi-select is an adoption blocker for Files.** New Discussion #12263, October 13, with replies through October 14: <https://github.com/microsoft/microsoft-ui-xaml/discussions/12263>. A community answer explains the preview’s `None`/`Single` selection modes and the spec’s future-work status for Multiple/Extended and `SelectedItems`; it does **not** promise those features in the first stable release. Files designer mdtauk says the app cannot adopt the control without fuller selection modes. For current multi-selection needs, the answer recommends ItemsView/ListView—useful guidance, not a maintainer release commitment.

- **TextBox prediction suppression needs Windows-side coordination.** Issue #8905, originally September 23, 2023; new investigation October 13: <https://github.com/microsoft/microsoft-ui-xaml/issues/8905#issuecomment-6153202902>. Microsoft contributor brene-msft identifies `IsTextPredictionEnabled="false"` not taking effect as a Windows 11 OS regression and reports filing a Windows bug. They do not believe a XAML-only workaround is possible without the Windows Text Framework team; a XAML change might also be needed. The issue remains open: a diagnosis, **not a fix or reliable workaround**.

- **NativeAOT collection errors get a more actionable explanation.** Issue #11248, originally July 17, 2026; new comment October 13: <https://github.com/microsoft/microsoft-ui-xaml/issues/11248#issuecomment-6155839597>. Contributor dotMorten recommends `AllowUnsafeBlocks=true` or explicit CsWinRT 2.3.1, which enables it, explaining that otherwise the necessary collection COM wrappers/interfaces are not generated—even for empty collections. The generic `E_INVALIDARG` then masquerades as an unhelpful XAML/class-factory failure. This is contributor guidance for the reported scenario; a clearer diagnostic is proposed, not verified implemented.
