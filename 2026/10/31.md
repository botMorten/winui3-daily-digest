## Community experience

- **A green formatting gate can hide broken WinUI analysis.** WindowsAppSDK issue, October 31: <https://github.com/microsoft/WindowsAppSDK/issues/6922>. A developer reports that 2.6.4’s design-time XAML inclusion adds generated files twice to Roslyn’s `MSBuildWorkspace`; their roughly 40-page app produces 36,311 errors, yet `dotnet format --verify-no-changes` can exit successfully. The same projects reportedly work on 2.5.1. Setting `EnableWinUIDesignTimeGeneratedXamlCompileItems=false` eliminates duplicates in the reporter’s test; this documented opt-out trades off the new design-time assistance. No maintainer-confirmed correction yet.

- **Tiny11 Builder ships a native WinUI application, not a PowerShell wrapper.** Project release, October 30, 07:46 PDT — **missed catch-up**: <https://github.com/ntdevlabs/tiny11builder/releases/tag/winui-v0.2.0>. The C#/WinUI 3 image builder supplies self-contained x64/ARM64 ZIPs, portable JSON recipes, English/Chinese UI with external translation catalogs, and navigation validation; 0.2.0 adds offline update integration and clearer accessibility labels. It is a concrete WinUI adoption example with substantial background work and resumable workflows—not a framework performance benchmark. Packages are unsigned; Core removes security/servicing capabilities, and the project explicitly requires isolated-VM testing of output.

## News/releases

- **Packaged versus unpackaged becomes a template choice—in merged source.** WindowsAppSDK PR, merged October 30: <https://github.com/microsoft/WindowsAppSDK/pull/6905>. .NET WinUI and project-based Reactor templates default to Packaged and offer Unpackaged, generating appropriate properties, assets and launch profiles instead of requiring manual conversion. An important source-level detail: unpackaged scaffolds still explicitly include MSIX BuildTools, despite the PR summary’s broader wording. The single-file Reactor template does not expose this option. No released template distribution containing the merge was verified.

- **ARM64EC startup failure gets a maintainer’s next-release commitment.** Issue opened October 29; new October 30 response: <https://github.com/microsoft/WindowsAppSDK/issues/6911#issuecomment-6530149763>. Scottj1s says the fix “will be included in next release,” and the issue closes. The reported 2.6.4 failure involves named `USER32!TransformPoint` imports in two ARM64EC DLLs. This advances the previously reported investigation, but closure is not shipment; the suggested fallback to 2.5.1 was not runtime-validated in that investigation. No new WindowsAppSDK release appeared in the primary window.

## microsoft-ui-xaml — past 24 hours

**Exact window:** October 30, 08:30 → October 31, 08:30 PDT. Direct all-state Issues and enabled Discussions were inspected, including older parents and replies. Six substantive threads:

- **DLL activation now respects added search directories.** Issue opened October 4; new October 30 maintainer contribution: <https://github.com/microsoft/microsoft-ui-xaml/issues/12158#issuecomment-6529671932>. JesseCol confirms the main-branch fix, independently matched to merged PR #12428: activation switches to `LoadLibraryExW` with default-directory search flags, restoring `AddDllDirectory` behavior. Separate WebView2 initialization-recovery concerns remain deferred; their AI-originated diagnosis is unconfirmed. **Source fix, not verified package shipment.**

- **Cross-GPU corruption: more topology evidence, less confidence in a universal workaround.** Issue opened October 28; four new developer comments October 30–31: <https://github.com/microsoft/microsoft-ui-xaml/issues/12434>. A Store app built with SDK 2.5.1 shows the same corruption; another reporter says the symptom follows the secondary-display role when primary displays swap. Explicit GPU preferences repair Notepad for some configurations, while another report says neither preference repairs Paint. Practical implication: test display roles and per-app GPU preferences, but do not call this a 2.6.4-only defect or confirmed fix. Related adapter-recovery PR #12198 remains unmerged.

- **Detached ItemsRepeater plus GC can make ordinary collection edits crash.** New October 30 issue: <https://github.com/microsoft/microsoft-ui-xaml/issues/12488>. A minimal 2.6.4 repro detaches a repeater, forces GC, then gets `E_FAIL` from `Clear`, `RemoveAt` or `Insert`; no-GC and append controls pass. The author reports replacing the bound list passes the same harness. This narrows older intermittent crashes, but subscription/lifetime analysis and workaround remain reporter evidence, not maintainer confirmation.

- **Icon-only top NavigationView parents get their chevrons back.** Issue opened December 2023; October 30 PDT merge/closure: <https://github.com/microsoft/microsoft-ui-xaml/issues/9139>. PR #12332 removes clipping caused by a fixed presenter width and invalidates cached widths when item visuals change, also allowing items to return from More without resizing. This is materially new versus the earlier draft coverage. **Merged source; release inclusion unverified.**

- **Wheel scrolling followed by animated return-to-top triggers a layout cycle.** New October 30 issue: <https://github.com/microsoft/microsoft-ui-xaml/issues/12490>. A 2.6.4 ScrollView/ItemsRepeater/StackLayout repro with variable-height items reaches `AG_E_LAYOUT_CYCLE`. A minimal project and traces are supplied; the only new reply is AI-assisted bot triage. No confirmed diagnosis or workaround.

- **Persistent menu cursors gain an instrumented repro.** Issue opened September 2023; new October 30 comment: <https://github.com/microsoft/microsoft-ui-xaml/issues/8829#issuecomment-6532894470>. The developer samples cursor state every 2 ms and connects failures to popup/shadow margins. A community mitigation uses `FlyoutShowOptions.ExclusionRect` to keep the popup clear of the pointer; exact context-menu clearances were not visually verified on the test laptop. Useful diagnostic progress, not an upstream fix.
