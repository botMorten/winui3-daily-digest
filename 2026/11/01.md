## Community experience

- **MSIX error-reporting extension fails on an alternate installation drive — catch-up.** WindowsAppSDK issue, **October 30**. A developer reports SDK 2.6.4 MSIX installation failing with `0x80073CF6` while registering `windows.diagnosticServiceModule.undocked` after changing the new-app storage location to E:. The supplied manifest uses `windows.diagnosticServiceModule` and `mscordaccore.dll`; the environment is Windows Insider build 26300.9711. There is no maintainer confirmation or verified workaround. Practical implication: include non-default installation volumes in deployment testing, particularly when enabling diagnostic modules for self-contained .NET packages; do not generalize this single Insider-build report to all WinUI apps. <https://github.com/microsoft/WindowsAppSDK/issues/6917>

## News/releases

- **TabView template’s restore-exception clamp is now merged — catch-up update.** Microsoft source change, **October 27**. Earlier coverage described the proposed remedy for transient negative `AppWindow.TitleBar.RightInset` values causing an `ArgumentException` when assigned to `MinWidth` during minimize/restore. PR #6869 has since merged into main: both the WinUI and Reactor TabView templates apply `Math.Max(0, …)` before DPI conversion. Existing generated apps can inspect this small source change rather than waiting for new scaffolding. This verifies a source-merge milestone, **not shipment in a template package or Visual Studio update**. <https://github.com/microsoft/WindowsAppSDK/pull/6869>

- **MSIX External Location: keep your installer, add package integration — catch-up.** Howard Kapustein, Microsoft Inside MSIX blog, **October 27**. The explainer clarifies an existing deployment option: externally installed payload files can participate in package integration while footprint files such as `AppxManifest.xml` remain packaged. The external installer—not MSIX—still owns payload installation, repair, security and uninstall. Both `AllowExternalContent=true` and an installation-time External Location are required. Useful for desktop teams retaining an established installer while adopting Windows integration; this is guidance, not newly released SDK functionality. <https://devblogs.microsoft.com/insidemsix/msix-external-location/>

No newer Windows App SDK release was found in the inspected official sources; October 27’s 2.6.4 remains the latest verified release and is not repeated as news.

## microsoft-ui-xaml — past 24 hours

Exact window: **October 31, 09:30 PDT → November 1, 08:30 PST**. Issues of all states and GitHub Discussions were checked directly; pull requests and routine bot/label churn were excluded from these stories.

- **Issue #12495 — new ItemsView/LinedFlowLayout lifetime-crash reproduction.** Opened **October 31, 14:48 PDT**. The reporter’s packaged C#/.NET 10 sample replaces an ItemsView every 200 ms and forces GC, producing a native `0xC0000005` access violation with SDK 2.6.4. Their comparisons did not crash with StackLayout, ItemsSource replacement, or reattaching the same control; waiting for `Unloaded` did not help. This narrows what to test in dynamic views, but the root cause and fixes remain unconfirmed. <https://github.com/microsoft/microsoft-ui-xaml/issues/12495>

- **Issue #12158 — new WebView2 regression-validation harness.** Original issue **October 4**; new comment **October 31, 14:29 PDT**. David Lechner supplied a Python/uv reproducer covering both `EnsureCoreWebView2Async` and Source-first initialization, with a 1.8 baseline, loaded-DLL diagnostics, PASS/FAIL exits and a 30-second timeout. Yesterday’s coverage concerned the DLL-search source fix; today’s advance is a concrete way to validate it, not evidence that validation passed or a fixing package shipped. <https://github.com/microsoft/microsoft-ui-xaml/issues/12158#issuecomment-6549375655>

- **Issue #8829 — cursor workaround becomes an integration helper.** Original issue **September 4, 2023**; new comment **November 1, 07:18 PST**. HO-COOH linked WinUIEssentials’ CursorController; its README documents calling `ApplyCursorWorkaround()` once after launch for the ContextFlyout/ComboBox wrong-cursor problem. This is a newly offered community integration option beyond yesterday’s timing/reproduction discussion. Effectiveness remains author-claimed, not independently tested or an upstream framework fix. <https://github.com/microsoft/microsoft-ui-xaml/issues/8829#issuecomment-6559868255>
