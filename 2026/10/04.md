## Community experience

- **New MSIX build tools can load an older PRI task during AOT debugging.** WindowsAppSDK issue, **October 4**. A developer using SDK 2.5.1, Visual Studio 2026 and `<PublishAot>true</PublishAot>` reports that BuildTools.MSIX `1.7.260930100` fails with MSB4064/MSB4063: the loaded older `WinAppSdkExpandPriContent` task does not accept `UseSharedPriExpansionCache`. Removing older package versions from the local NuGet cache reportedly restored F5; inspect the assembly path in the error before applying that workaround. This is a useful counterpoint to the packaging fixes covered Friday, but currently a single-reporter finding with no maintainer response or shipped correction. <https://github.com/microsoft/WindowsAppSDK/issues/6841>

- **RichEditBox scrollbar theming and cursor behavior: two concrete answers.** Stack Overflow, questions/answers **October 3–4 Pacific**. For a white scrollbar that needs programmatic theming, an accepted answer recommends finding `ScrollBar` descendants after the editor loads and setting their `RequestedTheme`; another accepted answer suggests a `RichEditBox` subclass assigning an arrow `ProtectedCursor`, claiming the inner text surface retains its I-beam. Both are full-source human Q&A verified through the public API, not synthetic search results; neither workaround was executed here or confirmed by a maintainer. Questions: <https://stackoverflow.com/questions/80007777/how-can-i-change-the-theme-of-a-richeditbox-scrollbar-via-code-in-winui-3> · <https://stackoverflow.com/questions/80007760/best-way-to-fix-wrong-cursor-on-richeditbox-scrollbar-in-winui-3>. Answers: <https://stackoverflow.com/a/80007785> · <https://stackoverflow.com/a/80007767>.

- **Catch-up: scrolling while selecting text needs explicit event handling, according to an answer.** Stack Overflow, question **October 2 Pacific**, answer **October 3, 05:26 PDT**. The reporter says RichEditBox—including Gallery—stops responding to the mouse wheel during selection; the accepted answer attributes this to pointer capture and upward event routing, then handles `PointerWheelChanged` with handled-events support and calls the inner `ScrollViewer.ChangeView`. That is a concrete starting point for editor authors to test, not a verified root cause or SDK fix. <https://stackoverflow.com/questions/80007636/how-to-make-richeditbox-scrollable-while-highlighting-text> · <https://stackoverflow.com/a/80007677>.
