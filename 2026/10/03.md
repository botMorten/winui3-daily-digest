## Community experience

- **RibbonSpace 1.1.0 brings an Office-style ribbon to plain WinUI 3** — Wiesław Šoltés / GitHub, **Oct 3**. `RibbonSpace.WinUI` shares controls, MVVM, themes, KeyTips and backstage code with the Uno version, but **does not require Uno** in a WinUI app. The port documents explicit XAML namespaces, separate theme dictionaries, subclass style keys and PRI/XBF packaging; the author reports passing x64 CI and ARM64-VM runtime tests. For opaque “XamlCompiler.exe exited with code 1” failures, its diagnostic workaround is Visual Studio MSBuild with `UseXamlCompilerExecutable=false`. Release: <https://github.com/wieslawsoltes/RibbonSpace/releases/tag/v1.1.0> · Lessons: <https://github.com/wieslawsoltes/RibbonSpace/blob/main/docs/winui-differences.md>

- **Energy Saver debate: fix the old contract, or make apps migrate?** — WindowsAppSDK issue, **May 15; new comments Oct 2**. Two developers added three comments arguing that the existing on/off API should report **On** whenever Energy Saver is active, instead of requiring `EnergySaverStatus2` and feature detection; one needs the underlying Win32 notification fixed, not merely the SDK wrapper. The issue describes Standard mode incorrectly appearing as Off—relevant to throttling background work or animation—but the new comments establish neither a maintainer decision nor a shipped fix. <https://github.com/microsoft/WindowsAppSDK/issues/6483#issuecomment-5960930527>

## News/releases

- **Catch-up: MSTest/MTP guidance for unpackaged WinUI testing** — Microsoft Learn, **Sept 30; updated Oct 1**. The guide covers packaged, unpackaged and AppContainer WinUI 3 hosts; its full matrix requires MSTest **4.5** and Microsoft.Testing.Platform **2.5**, using matching previews until stable versions ship. MTP can launch an unpackaged executable directly, unlike VSTest's manifest-dependent WinUI provider: publish the window dispatcher for `UITestMethod`, propagate the exit code, and close the application so unattended runs finish. The sample also clarifies that `WindowsAppSDKSelfContained=true` bundles the SDK runtime, **not** the .NET Desktop Runtime. <https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-mstest-winui>

- **Catch-up: MSIX extension updates move to Visual Studio Installer** — WindowsAppSDK Discussion, **Sept 28; maintainer clarification Oct 1**. The Marketplace copy of Single-project MSIX Packaging Tools remains usable but is frozen; future updates come through Installer-managed WinUI development components, which take precedence without first uninstalling the Marketplace copy. After a developer asked about timing, the maintainer named **VS 2026 18.12 Insiders 1**, with stable **18.12** currently planned but subject to validation—not confirmed availability. Existing Installer-managed users need no migration; project/debug settings are retained. <https://github.com/microsoft/WindowsAppSDK/discussions/6813> · Reply: <https://github.com/microsoft/WindowsAppSDK/discussions/6813#discussioncomment-18701913>

## microsoft-ui-xaml — past 24 hours
**Exact window:** October 2, **08:32:01 PDT** → October 3, **08:32:01 PDT**. All entries below are **Issues**, including older threads with verified new comments.

- **LinedFlowLayout crash: deterministic repro plus suggested workaround.** Newly filed **Oct 2**, #12148 reports experimental **2.5.4** crashing 4/4 times when an image-bearing ItemsView changes from zero height to 400; the debugger shows an empty frozen range reaching element lookup. The reporter suggests deferring `ItemsSource` assignment through a low-priority dispatcher enqueue after `Loaded`; no replies or maintainer-confirmed fix. <https://github.com/microsoft/microsoft-ui-xaml/issues/12148>

- **Image locking: same file, different URI, different result.** On #633 (**2019**), a new **Oct 2** comment from dotMorten reports App SDK **2.5.1** blocking PNG overwrites with `ms-appdata:///` even after clearing `Image.Source`, while `file:///` to the same file succeeds. Copilot-assisted source analysis proposes retained memory-mapped bytes without write sharing; the URI switch is the reported workaround, and forced GC is diagnostic—not a production fix. <https://github.com/microsoft/microsoft-ui-xaml/issues/633#issuecomment-5958570458>

- **WMC9999 narrowed to overload discovery.** On #1114 (**2019**), dotMorten's new **Oct 2** App SDK **2.5.1** tests show generic/non-generic static `GetList` overloads working separately but failing together in one declaration order; renaming both to `ReadList` succeeds. The Copilot-assisted attached-property-filtering diagnosis remains a hypothesis, not a debugger-confirmed compiler fix; reordering is explicitly not robust. <https://github.com/microsoft/microsoft-ui-xaml/issues/1114#issuecomment-5960316048>

- **Popup work-area limits: usable workaround, substantial complexity.** On #11945 (**Sept 19**), **four new Oct 2 comments from two participants** describe a zero-sized topmost window hosting a XAML island with `ShouldConstrainPopupsToWorkArea=false`. The other participant objects to island complexity and argues for reduced mouse travel/accessibility; the related prototype remains open and explicitly “do not merge,” not shipped. <https://github.com/microsoft/microsoft-ui-xaml/issues/11945#issuecomment-5962804286>

- **Update: async XAML proposal reaches thread-affinity debate.** Yesterday's #12142 gained **two comments from two participants on Oct 2**, discussing background parsing/XBF compilation followed by object creation on the XAML/STA thread. This adds a design direction, not an implemented `LoadAsync`, verified speedup or maintainer commitment. <https://github.com/microsoft/microsoft-ui-xaml/issues/12142#issuecomment-5965216294>

- **Slider steps with nonzero Minimum.** Newly filed **Oct 3**, #12153 reports **2.4.0** selecting even intermediate values with `Minimum=1`, `Maximum=31`, `StepFrequency=2`, rather than odd values anchored to Minimum. Test your allowed values before relying on this configuration; no comments, confirmed workaround or fix yet. <https://github.com/microsoft/microsoft-ui-xaml/issues/12153>
