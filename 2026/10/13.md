## Community experience

- **AI screenshot descriptions: Microsoft reproduces the text-heavy UI refusal.** WindowsAppSDK issue #6855, opened **October 11**, with a **new October 12 response**. Yesterday's report covered a developer's finding that ordinary app screenshots returned `ImageHasTooMuchText`, even with `AccessibleDescription`; the change today is that Microsoft responder es0m-msft says, “I can repro” and promises to address it in the next release. This is Windows App SDK AI functionality, not a WinUI rendering defect. Treat it as a reproduced bug with a planned fix—not a shipped fix or a guarantee about which package will contain it. Apps relying on generated accessibility descriptions still need a useful failure path. <https://github.com/microsoft/WindowsAppSDK/issues/6855#issuecomment-6133932060>

- **Push-notification onboarding remains a production dependency, not just an API call.** WindowsAppSDK issue #6574, originally **June 21**, newly active **October 13**; first coverage of this thread here. The original reporter describes a Store-distributed WinUI 3 app that obtains a channel and backend token but receives WNS `403`, while the documented package-family-name/Entra mapping mailbox bounces. Today's commenter reports also waiting weeks for an email response. That corroborates the waiting problem, not the original reporter's entire technical diagnosis; no new Microsoft resolution appears in the inspected comments. Practical implication: validate the provisioning/mapping process early when scheduling a push-enabled release. This is separate from the already-covered Flutter/SDK sideloading report. <https://github.com/microsoft/WindowsAppSDK/issues/6574#issuecomment-6148486229>

## News/releases

- **WinUI Gallery 3.0 makes experimental controls substantially easier to evaluate.** Microsoft #ifdef Windows, **October 13**; linked Gallery release **v3.0.4**, published the same day. The Gallery now ships self-contained on **Windows App SDK 2.5.4-experimental**, rather than waiting for controls to reach stable before demonstrating them. Concrete examples include TableView sorting/grouping/editing/validation and 1,000 virtualized rows; live Charts; InkCanvas/InkToolbar; WrapPanel/LayoutPanel/PagerControl; and logical-pixel window size constraints. Developers can inspect working samples while API feedback can still influence design—but the experimental APIs may change or disappear and Microsoft explicitly says not to use them in production yet. Gallery-specific improvements include accessibility fixes, searchable control tags and removal of the separate `.wapproj`; these are not evidence that every corresponding framework bug is fixed. <https://devblogs.microsoft.com/ifdef-windows/winui-gallery-3-0-is-here-tableview-charts-inkcanvas-and-more/> · <https://github.com/microsoft/WinUI-Gallery/releases/tag/v3.0.4>

## microsoft-ui-xaml — past 24 hours

**Exact window:** October 12, **08:30 PDT** → October 13, **08:30 PDT**. Both Issues and GitHub Discussions were checked directly, including older threads with new activity.

- **Reused UserControls: stale text was traced to binding lifetime, not the collection control.** Issues **#10525** (April 2025) and **#11177** (June 2026), new contributor explanations **October 13**. `gpaskaleva-msft` reports confirming that inner `x:Bind` defaults to `OneTime`: the template changes the UserControl's `Data`, but its text does not refresh. Their sample fix is `Bindings->Update()` in the setter, or `OneWay` **with property-change notifications**—changing binding mode alone is insufficient. This is confirmed guidance for the supplied repros, not a new framework patch. <https://github.com/microsoft/microsoft-ui-xaml/issues/10525#issuecomment-6145607785> · <https://github.com/microsoft/microsoft-ui-xaml/issues/11177#issuecomment-6145760154>

- **NavigationView crash proposals became merged source.** Older issues **#10757/#10894** closed **October 12** after PR #12235 merged weak-reference handling for callbacks on dynamically removed items. Separately, **#9190** closed after the OpacityTransition/compositor fix merged. The #10757 reporter acknowledged closure, but did not report a package retest. These update yesterday's open-proposal coverage: **merged into main, not verified shipped**. <https://github.com/microsoft/microsoft-ui-xaml/issues/10757> · <https://github.com/microsoft/microsoft-ui-xaml/issues/10894> · <https://github.com/microsoft/microsoft-ui-xaml/issues/9190>

- **Windows 10 custom-title-bar border fix landed—with compatibility details.** Issue **#8948**, opened March 2023; **October 12** contributor response explicitly says the fix is in main, “not yet in a release.” It uses `Window.ExtendsContentIntoTitleBar`, not merely the AppWindow equivalent; all four Windows 10 border colors change, and the high-contrast caption-button gap is outside scope. <https://github.com/microsoft/microsoft-ui-xaml/issues/8948#issuecomment-6133645580>

- **IME candidate-window events now have an end-to-end prototype.** Issue **#12195**, opened October 7; **October 12** author update links open PR #12245 and says the fix spans **both XAML and Windows OS**. Japanese/Chinese/Korean testing is author-reported; the companion OS work remains under review. This is progress toward usable international search/autosuggestion, not an available downlevel workaround or a shipping commitment. <https://github.com/microsoft/microsoft-ui-xaml/issues/12195#issuecomment-6132796301>

- **C++/WinRT TwoWay binding exposes an IDL/code-generation usability problem.** New issue **#12241**, **October 12**, on SDK 2.5.1. The reporter gets C2039 when write-back needs a projected named-element accessor absent from IDL; adding a read-only IDL getter reportedly works. They acknowledge the documented IDL requirement and ask for consistent generation or a better diagnostic. No independent confirmation yet. <https://github.com/microsoft/microsoft-ui-xaml/issues/12241>

- **Launch-crash follow-up points toward local runtime damage, not a proven universal regression.** Issue **#12169**, opened September 30; **October 13** second-user tests found locale changes made no difference. Their installed x64 `CoreMessagingXP.dll` appears unsigned/versionless while the official redistributable's copy validates. Their failure occurs **before XAML parsing**, unlike the original report. This narrows their case; neither a corrupt official package nor a fix is established. <https://github.com/microsoft/microsoft-ui-xaml/issues/12169#issuecomment-6142202741>
