## Community experience

- **Windows ML initialization can pick the wrong deployment path in a DLL.** GitHub / WindowsAppSDK, **October 19**. PetrMinar reports an unpackaged 2.5.1 application where the EXE is self-contained but an ONNX-using DLL resolves `WindowsAppSDKMLDeploymentMode` to `Framework`; `OrtGetApiBase` then returns null. The reporter's workaround disables auto-initialization, copies the self-contained initializer implementation into the DLL, and sets the ML deployment mode to `SelfContained` so `onnxruntime.dll` is copied. This is a concrete warning for WinUI/Windows App SDK apps separating inference into native libraries: check the DLL's initialization and deployed dependencies, not merely the EXE's settings. **No maintainer response or independently verified fix was present at collection.** <https://github.com/microsoft/WindowsAppSDK/issues/6877>

- **Structured JSON request closed, but check channel support before changing production code.** GitHub / WindowsAppSDK, original issue **February 18, 2025**; new comment **October 19, 2026**. The original developer wanted a WinUI 3 app to select tools and emit parseable JSON, but reported extra prose around responses. Today, Microsoft contributor `connorMicrosoft` closed the request, saying structured output has been supported since summer 2026. The existing Microsoft guide describes schema-constrained generation through an experimental wrapper, status checking, limited schema keywords and higher latency; it still explicitly warns against production use of experimental APIs. Treat today's comment as confirmation that a structured-output path exists—not proof of stable-channel availability, full function calling, or a newly shipped fix. <https://github.com/microsoft/WindowsAppSDK/issues/5164#issuecomment-6268749917> · Guide, dated April 7/updated April 23 (background, not new): <https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-structured-output>
