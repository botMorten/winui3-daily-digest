## Community experience

- **Structured JSON: a silent operation is not necessarily a hung operation.** WindowsAppSDK issues, October 16: <https://github.com/microsoft/WindowsAppSDK/issues/6872> and <https://github.com/microsoft/WindowsAppSDK/issues/6871>. A packaged, self-contained WinUI C# repro on 2.5.4-experimental produced valid, 424-word JSON after about 82 seconds with zero progress callbacks; ordinary text generation did stream, despite the structured API also documenting partial-response progress. Separate trials exceeded a 25-second diagnostic bound on both current and previous experimental packages—not proof of an infinite hang or a new-version regression; practical lesson: keep native calls off the UI thread and distinguish absent streaming from failed completion, with no maintainer-confirmed fix yet.

- **OCR “catastrophic failure”: fresh retests narrow the problem, rather than identify a fixing release.** Original issue August 5, 2025; new replies October 16: <https://github.com/microsoft/WindowsAppSDK/issues/5684#issuecomment-6223715630>. After challenging a cannot-reproduce closure, Rafael Rivera retested successfully on Arm64/x64 Insider build 26340.9616 with SDK 1.7.x; Microsoft's Connor Al-Joundi separately reported six successful recognizer creations and working OCR on an AMD x64 Copilot+ PC with 2.5.1. These are useful positive compatibility observations, but neither reproduces the original Snapdragon/1.7 environment exactly or identifies the OS/model update responsible.

- **Accessible image descriptions: an ETA is promised, not a shipped fix.** Original reports October 10–11; new Microsoft replies October 16: <https://github.com/microsoft/WindowsAppSDK/issues/6852#issuecomment-6220846851> and <https://github.com/microsoft/WindowsAppSDK/issues/6855#issuecomment-6220840517>. Following earlier reproductions of corrupted “successful” descriptions and text-heavy UI screenshots being refused, Connor says he will follow up next week with an ETA on both. This updates previously covered issues without changing their release status: developers still have no identified public package/build to validate, and an accessibility feature cannot safely equate a success status with trustworthy output.

## News/releases

- **Missed coverage: identify the package actually running, not merely the executable you launched.** Inside MSIX, October 13: <https://devblogs.microsoft.com/insidemsix/find-msix-package-application-identity/>. Microsoft's practical walkthrough uses `TASKLIST /APPS /FI "PID eq …"` to retrieve a running process's package full name, then PowerShell/P/Invoke for its Application User Model ID, which Tasklist does not display. This is directly useful when diagnosing WinUI activation, notification identity, or side-by-side package registrations; it is a diagnostic technique, not a new SDK feature.

No newer Windows App SDK release was found in the directly checked GitHub release list. Gallery 3.0's October 13 announcement was already covered and is not recycled as today's news.

## microsoft-ui-xaml — past 24 hours

**Exact window:** October 16, 2026, 08:30 PDT → October 17, 2026, 08:30 PDT. Direct API inspection covered 11 issues and all 643 accessible Discussions, including every historical comment/reply tree; pagination and count-integrity checks completed.

- **Unpackaged WinUI unit tests: a concrete working sample, not just advice.** Issue [#11267](<https://github.com/microsoft/microsoft-ui-xaml/issues/11267>) opened July 22, 2026; [new October 16 response](<https://github.com/microsoft/microsoft-ui-xaml/issues/11267#issuecomment-6226907097>) attaches an unpackaged WinUI test project that contributor dotMorten says works and notes work on easier unit-test templates. The older explanation is that a separate test host does not execute the app's generated entry point/`OnLaunched`, so its UI initialization and dispatcher assignment never happen. Today's tangible addition is the sample; its success is contributor-reported, not independently executed here, and the template changes are work in progress—not a released template update.

- **NavigationView's property-order pane-opening bug gets a targeted draft fix.** Issue [#7609](<https://github.com/microsoft/microsoft-ui-xaml/issues/7609>) dates to August 16, 2022; newly linked [PR #12325](<https://github.com/microsoft/microsoft-ui-xaml/pull/12325>) opened October 17 UTC (late October 16 PDT). The contributor traces `IsPaneOpen=false` being overridden when it precedes `PaneDisplayMode=Left` to clearing `m_wasForceClosed` before template application. The inspected patch preserves that flag until the template is applied and adds API tests for both XAML and code property order. **Open draft, unmerged**; the description says fixed-path/regression results are pending despite a generic checked test box. No shipping fix is established.

- **NavigationView's clipped hamburger gets a first-render sizing diagnosis.** Older [#5854](<https://github.com/microsoft/microsoft-ui-xaml/issues/5854>) (September 9, 2021) and [#9034](<https://github.com/microsoft/microsoft-ui-xaml/issues/9034>) (October 30, 2023) both gained a link to [new October 16 draft PR #12321](<https://github.com/microsoft/microsoft-ui-xaml/pull/12321>). It identifies an initialization-order problem: the toggle width is copied while the template setting is still zero, falling back to 40px where 48px is needed. The inspected patch reapplies toggle sizing when the template width changes, with a first-render/runtime-size API test. **Open draft, unmerged; fix validation pending.** It explicitly does not address the separate blurry-Lottie-icon problem.
