## Community experience

- **New WinUI item templates leave substitution tokens in generated code.** WindowsAppSDK issue, November 12. After updating to Visual Studio 18.12 and the new WinUI templates, ghost1372 reports that adding a UserControl produces literal `__WINUI_USERCONTROL__` tokens in both XAML and C#; their follow-up shows the equivalent `__WINUI_RESOURCE_DICTIONARY__` problem. This is a concrete scaffolding failure to check after upgrading, not evidence that existing controls stopped working; no maintainer response or verified repair was present at cutoff. <https://github.com/microsoft/WindowsAppSDK/issues/6968>

- **Windows 10 startup crash traced by a developer to disposing ApplicationData.** WindowsAppSDK issue, November 11 Pacific / November 12 UTC. Nevca supplies a 2.6.5 repro where `ApplicationData.Dispose()` causes an access violation on Windows 10 22H2, while the same build succeeds on Windows 11; their packaged app encounters it through `using var data = ApplicationData.GetDefault()`. The author reports that omitting disposal avoids the crash and attributes it to forwarding to an unavailable OS interface. Treat that as a reporter-tested mitigation and diagnosis—not a maintainer-confirmed fix—and include Windows 10 in compatibility testing if you use these APIs. <https://github.com/microsoft/WindowsAppSDK/issues/6967>

- **Deployment API reportedly returns success for a rejected downgrade.** WindowsAppSDK issue, November 11. Gaoyifei1011 reports `AddPackageByUriAsync` returning `CompletedSuccess` with empty error fields even though Windows logs `0x80073D06` because a newer package is already installed. The report targets SDK 2.6.5; there is no verified workaround or maintainer conclusion. Practical implication: add an explicit downgrade case to deployment tests rather than assuming this report establishes that every successful result is unreliable. <https://github.com/microsoft/WindowsAppSDK/issues/6966>

- **Update: independent evidence for AppInstance startup hangs on runtime 2.6.5.** Original issue October 13; new comments November 12. A second developer supplies wait-chain/minidump evidence of Snipping Tool launches waiting on a mutex associated with a PID now belonging to an unrelated process; the original reporter follows up with a source-level explanation of why the newer runtime still appears vulnerable. Killing all affected app processes provided temporary recovery, not a permanent fix. The new capture strengthens the earlier PID-reuse report, but its author explicitly stops short of a deterministic replay or complete proof; no maintainer-confirmed resolution is shown. <https://github.com/microsoft/WindowsAppSDK/issues/6860#issuecomment-6822177838>

## microsoft-ui-xaml — past 24 hours

Exact window: **November 11, 2026, 08:30 PST → November 12, 2026, 08:30 PST**. Direct API inspection covered 29 updated issues across all states, excluding PRs, and all 649 current Discussions with their comment/reply trees. **No timestamp-verified Discussion activity** was found; the substantive activity below is in Issues.

- **ItemsView reset-scroll fix merged.** Original issue September 29; new merge/closure November 11. PR #12086 fixes nonanimated bring-into-view requests using the current UI-thread extent instead of allowing stale compositor bounds to re-clamp the target. A repeated-content-reset regression test accompanies it; animated scrolling is intentionally unchanged. This is verified source progress for apps resetting collections before scrolling—not evidence that a released NuGet package contains the fix. <https://github.com/microsoft/microsoft-ui-xaml/issues/12085>

- **TableView's custom editor stays open after Enter.** New issue November 12. DHancock supplies minimal XAML against **2.6.6 experimental**: Enter raises `CellEditEnding` with Commit and `Cancel=false`, yet the editor remains active. Esc closes it, but that is not a verified commit workaround. No human maintainer conclusion was present; test keyboard completion explicitly before adopting custom editing templates. <https://github.com/microsoft/microsoft-ui-xaml/issues/12644>

- **Source audit proposes correctness repairs, not measured speedups.** New issue November 12. A contributor's Clang-assisted audit reports incomplete variant-map clearing/cache invalidation, numeric-conversion fallback paths reading unwritten results, and missing `va_end` cleanup. The corresponding draft PR #12645 includes proposed repairs and tests, but remains open; the evidence is a focused source audit, not a released-package reproduction, merged fix, or benchmark. <https://github.com/microsoft/microsoft-ui-xaml/issues/12647>

- **Chart updates explain label fitting and RTL/accessibility fixes under review.** Original issues November 5; new contributor comments November 12. Nitin-100 describes preserving the application's fixed spacing while thinning labels in whole multiples until they fit, plus an RTL drawing correction that keeps glyphs readable and aligns Narrator bounds. These are useful implementation details beyond the earlier reports, but both patches are in internal review: their source/tests cannot be independently checked publicly, and neither is a verified shipped fix. <https://github.com/microsoft/microsoft-ui-xaml/issues/12572#issuecomment-6821970439> · <https://github.com/microsoft/microsoft-ui-xaml/issues/12570#issuecomment-6818864625>
